> 这篇文章记录的是我对 DSpark 的初步理解。具体的研究和设计还在学习中，目前正在尝试给 gLLM 推理引擎集成 DSpark。先写下了目前能讲清楚的主线、阅读收获写下来，后续会结合代码与实验继续更新。

## 1. 先弄清楚：投机解码（Speculative Decoding）到底在省什么

DSpark 中的两个部分，对应到我理解的两条主线：**怎样较快地产生质量更好的草稿，以及怎样决定这些草稿值得验证多长。**

大语言模型（LLM）的自回归生成是一个 token 接着一个 token 地推进。在小 batch 的 decode 场景中，推理常受 GPU 显存带宽（Memory Bound）等因素限制，逐 token 重复执行前向会带来较高延迟。

投机解码是一种常见的提速方法，可以先用“小秘书与大老板”的比喻来理解：

- 🧑‍💼 **草稿模块（小秘书 / Draft Model）**：用相对便宜的计算，先一口气猜测并写出一段候选 token。
- 👨‍💼 **目标模型（大老板 / Target Model）**：只用一次 Forward 计算，批量验证这份草稿，对的留下，错的删掉重写。

草稿既可以来自独立小模型，也可以来自复用目标模型部分组件的模块。

这里的“验证”不能简单理解成检查候选是否通顺。论文采用的标准投机解码会比较 draft 和 target 的概率分布，按拒绝采样规则决定接受哪些 token，以保持 target 的输出分布。**保持分布不变，也不等于每次运行都产生完全相同的文本。**

另一个很重要的约束是：接受的是连续前缀。例如候选有四个位置，第三个位置被拒绝，即使第四个位置单独看起来不错，也不能跳过第三个位置，把第四个直接接到输出里。

因此，一轮生成的收益不能只看“猜了多少个”，还要一起看草稿耗时、验证耗时，以及最后实际推进了多少个有效 token。论文用每轮耗时与接受长度的比值来描述这种关系（§2.1）：

$$
L = \frac{T_{\mathrm{draft}} + T_{\mathrm{verify}}}{\tau}.
$$

其中，`T_draft` 和 `T_verify` 分别表示每轮草稿生成与验证的耗时，`τ` 表示每轮平均接受长度（包含 target 额外生成的 token），`L` 则表示平均每个有效 token 的生成耗时。

这让我觉得，投机解码首先是一个成本与收益的问题。多做一次草稿计算是否划算，要看它最终替目标模型省下了多少轮生成。

理解 DSpark 的设计之前，可以先对比之前的草稿生成方式和固定长度验证策略的优势与局限：

| 方式 | 代表方案 | 优点 | 主要局限 |
| --- | --- | --- | --- |
| **自回归草稿** | Eagle3 | 后续位置可以利用已经采样的前缀，对块内 token 依赖进行建模。 | 草稿需要串行生成，延迟通常随草稿长度增加；更深的草稿网络也会增加每一步的计算成本；为控制延迟，实际配置往往采用较浅的网络，限制模型容量。 |
| **并行草稿** | DFlash | 多个位置在一次前向中计算，减少串行生成步骤，为使用更深的网络提供空间。 | 基础预测难以根据块内实际采样的结果逐步调整，可能把不同的合理接续混在一起，出现多模态碰撞和后缀接受率衰减。 |
| **固定长度验证** | 固定长度配置，如 MTP-1/3/5 | 验证预算固定，实现与执行形状较简单。 | 验证长度不随草稿质量和系统负载调整；高并发时，验证低收益后缀可能占用其他请求的计算预算，降低整体吞吐。 |

*前两行比较草稿生成方式，第三行比较验证长度策略，它们属于不同维度。并行草稿的一次前向，也不代表总计算量和耗时完全不受草稿长度影响。*

DSpark 采用了两个方式来解决  

1. 🚀 **第一招：半自回归生成（兼顾速度与连贯性）**  
架构：采用“重型并行骨干（Parallel Backbone） + 轻量串行头部（如 Markov 头/RNN）”。  
逻辑：先用并行网络在一瞬间生成粗糙的特征向量（极速），再用极轻量的模块顺手修饰上下文词语的连贯性。  
效果：既保留了并行生成“瞬间出草稿”的高速度，又解决了后续词语容易“胡言乱语”的前后矛盾问题。  

2. 🚀 **第二招：基于置信度的硬件感知调度（闲时多查，忙时少查）**  
置信度打分：给草稿里的每个预测词都打一个“置信度得分”（评估大模型接受该词的概率）。  
动态剪枝：系统根据当前 GPU 的实时负载情况，动态决定送入大模型验证的草稿长度：  
GPU 较闲时：算力有富余，哪怕草稿后半段置信度偏低，也顺手一起验证。  
GPU 较忙（高并发）时：算力极其宝贵，只检查置信度极高的前几个词，后面的直接剪枝扔掉，把算力优先留给其他请求。  

## 2. MTP 与 DSpark 的流程概览

下面是一张 MTP 与 DSpark 的简化流程示意图，用于概览两者的主要解码流程。上半部分是基于 MTP 模块的投机解码，下半部分是 DSpark 的半自回归草稿生成与置信度调度。


![修订后的 MTP 与 DSpark 简化流程示意](/images/papers/dspark/decoding-overview.png)

*流程概览：这是整理的简化示意，并非论文原图；模块内部计算和部分运行时细节在这里省略。*

阅读这张图时，可以注意几个边界：

- **MTP 的适用范围。** 上半部分以 DeepSeek-V3 式顺序 MTP 为参考，具体草稿长度与模块复用方式取决于推理实现。
- **Confidence Head 预测的是条件接受概率。** 更准确地说，是在前面的草稿均被接受的条件下，当前位置被接受的概率；调度还需要考虑整个前缀能存活下来的累计概率。
- **调度预算分支是简化表达。** 原图中“降低 Target 验证预算”的方向是对的，但论文的完整调度器还结合负载和引擎吞吐曲线，为各个请求选择验证前缀长度。保留的候选仍要经过 target 验证。
- **Target 补充的 token 要区分情况。** 草稿全部被接受时，会额外采样一个 bonus token；遇到拒绝时，则从修正后的分布重采样，不能把两者都简单标成 bonus token。
- **缓存更新是逻辑概括。** 拒绝后缀不能留在已确认上下文中，但不代表每个被拒绝的 token 都要立即释放一个物理缓存页。Page Table 保存的是缓存页映射，KV Cache 才保存实际的键值张量。

流程图说明“谁生成、谁决定验证长度、谁负责最终验证”，更细的状态和缓存变化，需要结合实现补充。

## 3. 半自回归：把顺序依赖放在便宜的地方

纯自回归草稿会逐个生成候选，后一个位置能够利用前面实际采样出来的 token，但草稿本身也有串行等待。纯并行草稿把多个位置的计算放到一次前向里，却难以根据块内已经采样出的结果继续调整后续预测。

这里的“并行预测缺少依赖”，不等于网络内部的各个位置完全不能相互注意。关键在于：**产生基础预测时，后面的位置还不知道前面最终采样出了哪个 token。**

论文用 “of course” 和 “no problem” 举例：它们分别都是合理的接续，但不同位置独立采样，可能把两条接续混成 “of problem” 或 “no course”（§3.1）。这个例子更容易理解，为什么每个位置分别看都有一定道理，拼到一起却未必连贯。

DSpark 的做法是把草稿生成分成两个部分：计算较重的并行 Backbone 先生成各位置的特征和基础 logits，再用轻量的顺序模块，根据已经采样出的前缀修正后续预测。

默认的 Markov Head 利用前一个 token 提供局部转移偏置，并与当前位置的基础 logits 合起来形成采样分布。论文也研究了能够保留更多块内历史的 RNN Head，但考虑到收益和部署复杂度，默认采用 Markov Head。

目前最有收获的是这种计算分工：**计算较重的部分尽量并行，确实需要顺序依赖的部分尽量轻量。** 

不过，“顺序模块很轻”也要看实验条件。论文报告的低延迟开销来自特定 batch size、上下文长度和引擎配置，不能据此断定在任何环境下增加它都几乎没有成本。

## 4. 为什么草稿更长、接受率更高，还不一定更快

半自回归主要改善草稿质量。接下来还有一个问题：即使已经生成了一整块候选，也不代表全部送给 target 验证最划算。

论文指出，草稿在不同任务上的可接受程度存在差异，数学、代码和开放式聊天的表现不同；同时，验证额外 token 的代价还取决于当前服务负载。负载较低时，多验证几个候选可能只增加少量耗时；负载较高时，它们会占据本来可以服务其他请求的计算预算。

所以，不能只问“这个候选有多大概率被接受”，还要问“为了它多花这些计算，是否值得”。

Confidence Head 为这个决策提供估计。假设前两个位置的条件接受概率都为 0.9，那么前两个位置一起存活的估计概率是 `0.9 × 0.9 = 0.81`。这个小例子也说明：后面的位置能否发挥作用，取决于前面能否一路被接受。

但模型给出的分数不一定就是可靠的概率。如果经常把实际只有六成的机会估成九成，调度器就会高估长草稿的收益。论文因此使用 Sequential Temperature Scaling（STS），从左到右校准前缀存活概率（§3.2.1）。目前理解的是它的必要性，具体校准过程还需要继续学习。

有了这些估计，调度器再结合引擎预先测量的吞吐曲线，比较增加验证长度带来的预期收益与执行代价。它是在多个请求之间分配预算，各请求保留的草稿长度可以不同。

这也修正了我对流程图的理解：图中的调度预算分支可以帮助入门，但完整方法不能只用“分数低就裁剪”来解释。它要优化的是系统最终产出的有效 token，而接受比例只是其中一个指标。

## 5. 读实验时，我需要先看清数字在回答什么

论文的离线主实验关闭了置信度调度，让不同草稿方法使用固定长度，以便比较草稿本身的质量。论文表 1 中的指标是每轮接受长度，而且按论文约定包含 target 生成的额外 token（§4.1、§4.2）。它支持的是草稿质量方面的结论，不能直接读成同等幅度的端到端提速。
[![论文表1：不同草稿方法在多个目标模型和任务上的每轮接受长度](/images/papers/dspark/paper-table-1-draft-quality.png)](/images/papers/dspark/paper-table-1-draft-quality.png)
*论文表 1：离线主实验比较的是每轮接受长度，用来观察草稿质量；它不直接等于端到端提速比例。 来源：[DSpark 论文 PDF，第 11 页](https://arxiv.org/pdf/2607.05147v1#page=11)。*

论文图 2 的逐位置分析也很有启发。前面的候选被拒绝，会使后面的位置失去被利用的机会。因此，第一个位置的质量尤其重要；而只看一个平均接受长度，又容易看不到后缀在哪里开始衰减。
[![论文图2：Qwen3-4B 上不同草稿位置的条件接受率](/images/papers/dspark/paper-figure-2-position-acceptance.png)](/images/papers/dspark/paper-figure-2-position-acceptance.png)
*论文图 2：每个位置只统计此前草稿均被接受的情况，展示的是条件接受率，区别于整段前缀的存活概率。 来源：[DSpark 论文 PDF，第 12 页](https://arxiv.org/pdf/2607.05147v1#page=12)。*

论文图 5 则展示了另一种容易误读的现象：随着阈值提高，聊天任务中送去验证的 token 的接受比例从 45.7% 升到 95.7%。这表明低价值后缀被有效过滤了，不能直接解释为草稿模型本身突然变得更准确，更不能只凭这个比例断定系统已经更快。
[![论文图5：置信度阈值对接受和拒绝 token 数量以及接受比例的影响](/images/papers/dspark/paper-figure-5-confidence-threshold.png)](/images/papers/dspark/paper-figure-5-confidence-threshold.png)
*论文图 5：绿色柱表示接受 token，斜线柱表示拒绝 token，蓝线表示接受比例。观察比例提高时，也要一起看每步接受 token 的数量。 来源：[DSpark 论文 PDF，第 15 页](https://arxiv.org/pdf/2607.05147v1#page=15)。*

线上实验回答的是另一层问题。作者在 DeepSeek-V4-Flash 和 Pro 的特定服务配置与真实流量下比较 DSpark 和 MTP-1。在匹配整体吞吐的比较中，报告的单用户生成速度提升分别为 60%–85% 和 57%–78%（§5.4、论文图 7）。

论文也专门解释了严格交互速度要求下那些非常大的吞吐增幅：此时基线已经接近运行边界，能承受的并发很小。这些结果更适合说明可服务范围的扩展，不能拿来概括所有场景的常规收益。

[![论文图7：DeepSeek-V4-Flash 和 Pro 在线服务的吞吐与单用户生成速度](/images/papers/dspark/paper-figure-7-serving-frontier.png)](/images/papers/dspark/paper-figure-7-serving-frontier.png)

*论文图 7：横轴是单用户生成速度（token/s/user），纵轴是每 GPU 的总体吞吐（token/s/GPU）。曲线对应论文的真实流量与引擎配置。 来源：[DSpark 论文 PDF，第 18 页](https://arxiv.org/pdf/2607.05147v1#page=18)。*

留下一个读实验的习惯：看到“提升多少”之前，先看基线、指标、约束和运行条件。以后如果做接入或复现，也需要自己的测量结果。

## 6. 算法走到推理引擎里，还有哪些事情

论文的系统部分让我意识到，算法里一句“动态选择验证长度”，落到实现里会牵涉更多工作。

例如，理论分析使用的代价曲线有平滑性假设，而实际硬件曲线可能出现台阶和局部性能下降。生产流水线还需要提前准备执行形状，不能总是等当前计算结束、读回置信度之后再决定下一步。

论文为此采用异步调度，用前两步的历史预测估计验证容量，当前候选仍依据当前的累计置信度排序（§5.2）。为什么这样的设计还能保持目标分布，需要结合“不利用未来候选影响当前准入”的条件理解。这部分我还没有完全掌握，尤其不能把它简化成“异步了就自然无损”。

变长验证也会影响执行方式：同一个 batch 里，不同请求保留的候选数不同，需要让算子高效处理，同时保留各请求的逻辑边界。论文介绍了展平执行和 marker tensor 等适配（§5.3）。我能理解为什么需要解决这个问题，具体怎样组织张量和注意力索引，还需要看代码。

把这些问题放到推理引擎接入中，我目前更愿意先追清楚一轮生成的数据与状态：上下文特征怎样交给 draft，候选怎样送去验证，接受和拒绝后怎样更新序列及缓存。固定长度的正确链路建立后，才有条件判断动态调度是否带来实际收益。

**草稿模型能够 forward，只证明了其中一个环节；完整服务的正确性和性能，还需要分别验证。** 这是我想在后续学习中一直保留的边界。

## 7. 以后待补充的问题

写下这篇心得，并不代表这些问题已经解决。接下来会弄清楚的是：

1. Markov Head 的修正具体怎样与基础 logits 结合？每个位置的采样分布怎样用于后续拒绝采样？
2. Confidence Head 的训练标签与前缀概率校准怎样实现？不同任务之间的校准误差会怎样影响预算选择？
3. 异步调度为什么能够避免选择偏差？论文附录 A 的反例，能否用一个具体的小例子推清楚？
4. 接受前缀、拒绝后缀和新采样 token，分别怎样改变下一轮的 token、位置与 KV 状态？

论文还指出了一个明确的局限：前缀调度裁掉的是验证工作，最初整块草稿的生成成本已经付出；对于本来就很难被接受的请求，这部分成本仍可能浪费（§5.4，Limitations）。这也提醒我，减少一个环节的无效计算，不代表整条链路已经没有浪费。

后续会用单独的文章记录源码中的核心机制、接入设计与实验复盘，再根据实现和测量结果修订目前的理解。
